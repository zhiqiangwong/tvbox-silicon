## Context

动机与范围见 proposal.md，外部行为见 specs/ios16-compatibility/spec.md。

实现仓库和 OpenSpec 根目录均为 `/Users/konvy-1054/www/ai/tvbox-silicon`，本规划位于仓库内 `openspec/changes/support-ios16`。主目录中的旧规划保留为迁移备份，后续只维护仓库内版本，不扩大代码搜索、Git 或修改范围。`origin` 为用户 fork，`upstream` 为原仓库，兼容工作在 `codex/support-ios16` 分支进行。

当前 `project.yml` 和 `Package.swift` 要求 iOS 17。约 31 个文件含 `@Observable`，环境注入、绑定、嵌套模型和 `withObservationTracking` 也依赖新观察机制。`GlassKit.swift` 已有新旧系统效果适配，可复用这一组织方式。

iOS 工程静态链接 OpenJDK Zero 与原生桥接，并嵌入 Python、Node.js；QuickJS 和 FFmpeg 也是执行链的一部分。JVM、libffi、Unicorn TCI、原生绑定与媒体脚本使用了 iOS 17 编译目标。Python 脚本不仅使用预编译解释器，也自行编译扩展；Node.js 使用预编译框架。修改 Info.plist 无法证明二进制可在旧系统加载。

此前缺少可用的完整 Xcode/iOS SDK 验证环境，后续命令出现 Xcode 许可尚未接受提示；实施开始时重新核实工具链、许可与 SDK 状态。目前没有旧系统运行证据。现有 JVM 源码审查仅说明未发现明确 iOS 17 硬性依赖，不是整个依赖链的兼容证明。

## Goals / Non-Goals

**Goals:**
- 将系统差异集中到必要的构建配置、观察机制适配和少量界面兼容入口，尽量保留业务接口与文件结构。
- 先用独立测试应用验证运行环境，再以小范围界面证明观察机制，最后迁移其他调用。
- 保持同一业务模型、存储格式及原有应用标识，允许装饰效果降级。
- 为后续上游合并提供可重复的最低版本构建与核心运行检查。

**Non-Goals:**
- 不自行完整实现 Observation，不承诺宏、属性包装器和所有 SwiftUI 调用零修改。
- 不为 iOS 16 复制整个 UI 或维护第二套 JVM、业务模型和 IPA。
- 不追求所有订阅来源通过，不借机调整插件协议、数据库或通用架构。
- 不自建更新服务器或扩展更新数据协议，不为此次侧载建立完整发布流水线。

## Decisions

### 1. 先验证两个高风险点，保持核心能力范围

先完成运行环境验证，再完成观察机制小范围验证；没有这些证据，不批量改动页面。若发现必须删除现有运行环境、改变最低系统目标或大幅重构才能继续，则先记录实证和最小备选方案，回到范围评审，不擅自降低验收要求。

在基准阶段，通过临时诊断配置或隔离的诊断工程将应用与本地包最低目标设为 16.0，执行一次全量诊断编译，保留配置和编译错误清单；此处允许编译失败，目的是提前发现依赖与接口问题，不将暂时降目标视为交付完成。诊断配置不得混入正式发布产物，主工程的最终配置更新和全量通过仍在集成阶段完成。

状态管理验证使用独立 iOS 验证 target，最低版本从建立时即为 16.0。先只编译候选观察依赖、最小模型、视图和必要的可复用生产代码，外部服务用测试替身隔离；不直接导入最低要求仍为 17 的整个 TVCore 包，也不把整个 Store、RootView 或未适配页面纳入验证目标。先证明刷新、绑定与生命周期语义，再把通过的模式迁移到真实 Store/播放会话及所需依赖；后者的应用集成验证不得冒充独立样例已完成。验证用替身只属于测试，不形成第二套业务实现。

原生运行环境同样使用最低目标为 16.0 的独立测试入口：JVM 优先复用 spike；Python、Node.js、QuickJS 和媒体依赖仅接入必要桥接与资源，避免隐式拉入完整 SwiftUI 应用。在执行各运行环境启动测试前，先确认测试入口可独立构建、安装并启动。

基准阶段先记录本地 Release 归档、签名和 IPA 封装方案；测试空入口建立后立即通过这条路径生成 IPA，经用户 iPad 的 TrollStore 安装启动，及早发现打包或安装条件问题，不等待全量迁移结束。

备选：直接全量替换接口。未采用，因为无法尽早发现预编译依赖或状态刷新阻碍，返工成本高。

### 2. 运行库统一支持 iOS 16，保留现有调用边界

保持 OpenJDK 版本与 Zero/TCI 的纯解释执行模式，以及 `EmbeddedJarHost` 到 `TVAppleRuntimeRequest` 的请求边界；不为操作系统版本新增两套插件协议。将 iOS 真机与模拟器的目标统一为 16.0，tvOS 与 macOS 原有值不变。

逐项核对 JVM、libffi、Unicorn TCI、JNA、Capstone、Keystone、FFmpeg、QuickJS 和 Python 原生扩展。对 Python 与 Node.js 先检查 framework 各切片的 Mach-O 最低版本、架构、链接依赖及新接口使用；已满足目标的预编译框架直接复用，确实不满足时才源码重建。不得通过修改版本元数据绕过验证，不默认升级或降级依赖。

使用编译器的可用性诊断发现未保护的新系统调用，结合二进制版本信息和实际装载测试确认产物。真机与模拟器分别构建，不能互换静态库。

备选：按系统加载两份运行库。未采用，因为目前无明确收益，增加包体、打包和调试成本。

### 3. 最低版本与缓存保持一致

以 `project.yml` 的平台最低版本为目标来源，`Package.swift` 和原生构建脚本保持一致。只在实际存在多处引用的脚本间添加一个小型共享 shell 配置，供构建、打包与测试脚本读取，不建设通用配置框架，也不增加用户开关。保留项目现有 Xcode 工程生成方式。

首次适配清理受影响的 iOS 原生构建目录及旧 Python wheels；后续使用包含最低版本、已有源版本/配方标识的轻量构建记录。现有配方缓存（例如 FFmpeg）优先复用。打包不能仅依据 libjvm.a 等文件存在就认为正确，记录不匹配时重建对应产物。macOS/tvOS 缓存不做无关清理。

备选：仅改四个脚本中的常量并手动清缓存。首次验证可用，但不足以防止后续复用旧产物，所以增加最小缓存识别。

### 4. Observation 优先使用成熟的向下兼容实现

不把 `@Observable` 当作可由运行时判断替换的普通函数。实现时先核对候选依赖的官方文档、最低系统版本、Swift 6 支持与许可，固定可用版本，验证模型标记、忽略观察标记、绑定、环境注入和手动追踪的完整链路。

小范围先用独立 target 中与 Store/订阅及播放会话结构对应的最小样例验证，随后在全面迁移阶段接入真实对象：异步搜索、嵌套模型变化、双向绑定、页面销毁重建、对象生命周期、播放器单例/会话复用以及 `withObservationTracking` 的订阅重建。优先选择新系统可走系统原生路径的方案；即使需要兼容标记，也保持业务属性和方法不变，禁止大量同名类型遮蔽系统类型。

通过后记录实际选型和迁移模式，再应用到其他模型及视图，包括延迟创建的列表行和弹层。若候选方案失败，再比较统一 `ObservableObject` 所需改动；该备选不能在没有证据时成为全量机械替换的默认方案。

**小范围验证结论与统一迁移模式（已由 `Packages/IOS16ObservationSpike` 证实）**：
- 选定 `pointfreeco/swift-perception` (`1.6.0`)。
- 模型层统一将 `@Observable` 替换为 `@Perceptible`，`@ObservationIgnored` 替换为 `@PerceptionIgnored`；在 `macOS 14+` 和 `tvOS 17+` 上宏自动同时合成 `Observation.Observable` 协议遵循。
- 视图层保持 `@Environment(Model.self)` 和 `.environment(model)` 原写法不变（由 `Perception` 内置的环境回退支持）；双向绑定使用跨平台别名 `@AppBindable`（`#if os(iOS)` 为 `Perception.Bindable`，其余平台为 `SwiftUI.Bindable`）；读取可观察属性的视图 `body` 及延迟闭包（`ForEach`、`sheet`、`navigationDestination`）使用 `WithPerceptionTracking` 包裹；手动观察追踪使用 `withPerceptionTracking`。

备选：自建观察宏或双模型。未采用，正确刷新、生命周期及未来 SwiftUI 行为的维护成本明显过高。

### 5. 界面兼容按实际使用范围封装

复用 `GlassKit`，必要时增加相邻的 iOS 兼容文件。普通方法只有在签名、语义及重载选择可靠时才保持同名，否则使用明确的兼容入口。包装内部使用 `#available`，iOS 17+ 保留现有系统实现。

- 新式 `onChange`：覆盖本项目实际使用的初始触发、旧值/新值语义，不简单替换为少参数版本而改变行为。
- 空状态页面：用现有布局和文字组件保留标题、描述、图标及操作。
- 歌词滚动：旧系统采用可用的滚动定位机制，保留当前歌词跟随和用户手动滚动行为。
- 动画、符号效果、触感：使用旧系统支持的动画或省略装饰效果，不影响播放和操作结果。
- 其他接口通过最低版本编译逐项识别，只为当前使用方式补齐能力。

备选：给每个页面添加独立版本分支。未采用，分散逻辑会增加后续合并冲突和漏改风险。

### 6. 使用现有验证入口，并记录实际环境

复用 JVM spike 与桥接测试；增加必要的 iOS 真机入口及最低版本参数，不把完整应用 UI 作为运行环境测试前提。运行环境先测受控样例（启动、JNI、网络/HTTPS、基本计算或脚本），再测与新系统对照的代表性真实来源，包括需要原生 guard 的 JAR 路径。

最低目标设为 16 的编译不能替代 iOS 16 的运行。先核实当前 macOS、满足 Swift 6 的 Xcode、可用 iOS 16 模拟器之间是否存在可运行组合，不默认旧 Xcode 能构建此仓库。如当前机器无法运行旧模拟器，使用兼容的另一台 Mac/执行环境；在环境补齐前保持该任务未完成。

验证三个维度：iOS 16 的 iPad 模拟器核心流程；用户 iPad 的真实安装、播放、内存与后台恢复；同一构建在 iOS 17+ 的核心回归。用户真机通过 TrollStore 安装，不要求系统升级或额外 JIT。对其他平台运行现有构建检查，涉及共享模型的变化补充针对性功能检查。

布局验收覆盖 iPad 全屏 → 紧凑分屏 → 全屏，检查选中栏目、详情/返回路径、“更多”入口、播放会话与控制是否连续；在支持分屏的模拟器上执行，用户设备具备该条件时用最终 Release 复核。另用一个 iOS 16 iPhone 模拟器验证订阅 → 详情 → 播放 → 返回及“更多”导航，覆盖 `RootView.phoneTabs` 与 iPhone 播放页面分支，不要求额外 iPhone 真机或穷举设备。

影视订阅之外增加以下代表性端到端验收，每类选择一个在新系统对照基准中可用的样例，覆盖旧系统模拟器上可执行的操作，并在最终 Release 真机验收中确认音频、锁屏及实际播放：
- 音乐：播放队列与切歌、迷你播放器、锁屏控制、后台播放与恢复，验证曲目、声音和状态一致。
- 直播：打开频道、切台，验证频道信息、加载状态和实际播放一致。
- 网盘：一种现有登录方式、登录结果刷新、文件列表与实际文件播放，验证登录及播放完整链路，不保存授权凭据。模拟器不具备的条件留待真机，不以解析出 URL 代替播放。

最终真机验收使用本地侧载路径生成的候选 Release IPA：以现有 iOS scheme 和显式 Release 配置执行 Archive，取归档中的完整 `.app` 放入 `Payload/` 后封装 IPA，保留资源和嵌入框架结构。该路径不依赖上游证书、描述文件或 App Store Connect 密钥，不设置 `APPSTORE` 编译标记。可用无开发者签名的归档作为 TrollStore 路径候选，但具体签名处理必须通过最小入口及最终应用的实际安装、动态库加载确认；记录归档签名设置、嵌入框架处理和安装方签名行为，不能把“已生成 ZIP”当作可安装。新系统安装需要重签时使用可用的本地安装条件，不因此改变编译配置。

`Scripts/testflight-upload.sh` 即使带 `--no-upload` 也依赖上游发布密钥、使用 App Store 分发配置并启用 `APPSTORE`，因此不得直接作为上述路径；只复用其适用的构建准备和符号检查。优先记录可重复命令，必要时增加薄的本地打包入口，不重构 TestFlight 脚本或建设新发布系统。

记录源码提交、配置、构建标识、IPA SHA-256 及安装方式；经 TrollStore 安装到用户 iPad，并用同一份 IPA 在 iOS 17+ 设备回归，设备须满足各自安装条件。若安装服务必须重新签名，记录签名前后校验值并确认应用二进制和资源与同一归档来源一致，不重新编译另一份回归产物。若修复后重新归档，则对新候选重新执行受影响的验收，确保报告对应实际交付产物。

归档后检查并实际验证 JVM 的 jimage/JNI 符号保留（现有 `-export_dynamic`、`STRIP_STYLE: non-global`、`ENABLE_DEBUG_DYLIB: NO` 等约束）、Python/Node.js 框架与 Python 扩展嵌入、签名及动态加载。三个运行环境均须在安装后的 Release 应用中完成启动和代表性请求，并完成受影响的核心流程。保留现有资源嵌入和符号保留机制；Debug、模拟器和独立样例结果仅作开发证据，不能替代此项。

备选：只跑新版模拟器或只检查框架 Info.plist。未采用，无法证明旧系统接口和运行库实际可用。

### 7. 旧系统更新入口采用最小兼容提示

当前 `ReleaseFeed` 固定读取上游版本源，更新筛选只比较版本号和平台下载链接，不能证明该 IPA 支持 iOS 16。复用现有版本信息与更新展示，在 `Updates` 及其操作入口集中区分系统：iOS 16 仍显示发现的上游版本，但明确说明需等待或使用经过本兼容流程验证的构建，将直接获取上游包的按钮替换为兼容说明；不以版本号较新推断兼容性，也不把“有上游更新但未验证”报告为“已经是最新版本”。iOS 17+ 保持现有提示、链接及分发行为。

自动弹出的更新提示与手动检查共用该策略，不新增服务器、兼容版本数据库或用户开关。用受控更新数据验证上游发布新版本时两类系统的不同提示和按钮行为；最终 Release 在 iPad 确认入口，在新系统回归原行为。兼容构建仍按交付记录手动获取和安装，安装说明明确这一限制。

备选：新增专门的兼容更新源。暂不采用，因为当前是本地兼容交付，集中提示即可避免误导，新增服务会增加持续维护成本。

## Risks / Trade-offs

- [Xcode、Swift 6 与旧模拟器无法在当前 macOS 组合运行] → 最先确认工具链矩阵；必要时换验证主机，不把换工具链等同于修改业务代码，也不伪造通过记录。
- [误用 TestFlight 打包导致凭据阻碍或功能开关变化] → 先验证无需上游凭据、不启用 APPSTORE 的本地 Release 侧载路径，再用于最终应用。
- [上游更新包仍要求 iOS 17] → iOS 16 保留版本信息并提示需兼容构建，不直接推荐未经验证的下载；新系统行为不变。
- [全屏验证遗漏紧凑布局分支] → 增加 iPad 分屏切换和一个 iPhone 模拟器的核心流程检查，不扩大设备矩阵。
- [OpenJDK 或预编译依赖含旧系统不可用符号] → 完整重编译、启用相关可用性诊断和检查依赖，再做实际装载与功能验证；局部修补优先。
- [Debug 正常但 Release 归档裁剪符号或嵌入资源不完整] → 检查归档后实际产物并通过 TrollStore 真机验证 Java/Python/Node.js；同一候选安装包完成新系统回归。
- [观察机制迁移后静默不刷新或重复创建会话] → 小范围先验证嵌套数据、异步、绑定及生命周期，再批量适配；保留有业务意义的回归用例。
- [旧设备内存和解释执行速度不足] → 在用户 iPad 记录首次插件准备、热启动和连续操作；仅处理实际阻断问题，不先重写内存策略。
- [上游持续引入新接口] → 独立提交、集中兼容入口，每次合并检查新接口、观察模型与原生依赖，并运行最低目标构建；不承诺零冲突。
- [来源网络波动造成误判] → 受控样例先行，真实来源与对照系统复测，分别记录来源失败与系统兼容失败。
- [视觉一致性与交付成本冲突] → 保留可读内容、入口和功能语义，接受 iOS 16 装饰效果简化。

## Migration Plan

1. 在实现仓库检查工作区，记录基准；构建前按 AGENTS.md 获取 `upstream` 和 `origin` 更新，将 `upstream/main` 合入兼容分支并检查相关 fork 变更；仅未发布的本地提交可选择 rebase，不覆盖用户工作。
2. 独立提交运行库构建/缓存兼容及测试入口，通过 iOS 16 运行验证后形成第一阶段报告。
3. 在已设为 iOS 16 的独立 target 中验证观察机制样例，确认可行性并更新工作量；通过后迁移真实 Store/播放会话，最后扩展到其他页面，不依赖主工程先完成全量适配。
